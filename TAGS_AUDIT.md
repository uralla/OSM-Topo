# TAGS_AUDIT.md — Аудит стиля Garmin `uralla` (mkgmap)

**Статус:** рабочий документ, режим аудита. Ничего из перечисленного ниже не внесено
в реальные файлы стиля — это накопленный список решений/находок/открытых вопросов
для дальнейшего внедрения.

**Контекст проекта:** карта НЕ является generic-стилем. Специализация — лесной пеший
и велосипедный туризм (регион — предположительно Урал, судя по `landuse_points` и
названию `uralla`). Автор карты не программист, стиль собирался годами из разных
источников, отсюда накопленные несостыковки. Параллельно ведётся обсуждение с ChatGPT
(через API, история частично утеряна из-за лимитов) и Qwen3 (локально). Этот файл —
попытка синхронизировать три параллельных ревью в одну точку правды.

**Роль каждого участника:** независимо сверять с реальными файлами стиля/TYP, не
принимать выводы других моделей на веру, различать: confirmed bug / likely problem /
optimization / aesthetic choice / unresolved question. Не переписывать уже
зафиксированные решения пользователя без новых доказательств.

## 2. Хаки, которые выглядят как баги, но по факту — не совсем

| Место | Что смущает | Что оказалось при проверке |
|---|---|---|
| `lines:609` `highway=* & tunnel=yes {add name='туннель'}` | Похоже на no-op | `add` в mkgmap = «установить, если тег ещё не установлен» → рабочий приём: даёт дефолтное имя безымянным туннелям, не no-op |
| `inc/water_lines:7-14` `taxi=yes` на реках | Похоже на грязный роутинг-хак | Комментарий в коде: «роутинг по рекам — линия с синими стрелками направления течения». Вероятно осознанная фича — маршрутизация для сплава/рафтинга через слабоиспользуемый профиль `taxi`. **Не удалять**, но протестировать реальный маршрут на приборе/BaseCamp прежде чем менять |
| `points:380-395` `building=yes/true & mkgmap:area2poi!=true → 0x2b07` (тип «изба») | Изначально казалось «все здания → избушки», один из самых опасаемых пунктов | `points`-файл обрабатывает только узлы (nodes), не полигоны. Обычные здания (way-полигоны) корректно рисуются в `polygons:40` как `0x13`, это правило их не касается. `mkgmap:area2poi=true` появляется только при включённой опции `--add-pois-to-areas`, которая сейчас закомментирована в обоих `.args`. **Реальный текущий эффект ограничен** (задевает только редкие настоящие point-теги building=yes). Но: (а) семантически неверно — не «изба», (б) скрытая зависимость от опции, которая может быть включена в будущем и тогда неожиданно испортит карту. **Confirmed problem, но не urgent** — убрать из цепочки `0x2b07`, задокументировать `[IMPORTANT]` |
| `version` файл = `1`, `info` файл `version=3.0` | Ранее (в другом ревью) расценено как несоответствие для исправления | `version` — версия ФОРМАТА style-файла в спецификации mkgmap (не про сам стиль), `info: version=3.0` — версия стиля автора. Два разных смысла, **синхронизировать не нужно**, `version=1` оставить как есть |

## 3. Устаревшие/legacy OSM-теги — что уже обработано правильно, что нет

### Уже обработано защитным образом (подтверждено, трогать не надо)
- `highway=unsurfaced` (deprecated с 2007-2008, замена — `surface=unpaved`) → `lines:52,214` уже конвертирует в `track` + `mkgmap:unpaved=1`
- `ford=yes` / `highway=ford` — оба варианта покрыты параллельно в `lines` и `points`
- `leisure=nature_reserve` / `landuse=nature_reserve` / кривые формы `natural_reserve` — уже все 4 варианта вместе в `polygons:100`
- `landuse=cemetary` (опечатка) / `landuse=cemetery` — оба варианта через `|` в `inc/landuse_polygons:5-6`

### Найденные пробелы (тега нет вообще в стиле, хотя используется мапперами)
Проверено через OSM Wiki (не по памяти — она тоже может быть неактуальной):

| Тег | Статус проверки | Комментарий |
|---|---|---|
| `boundary=protected_area` (+`protect_class=*`) | подтверждено, современная схема охраняемых территорий (нацпарки/заповедники) взамен одиночного `leisure=nature_reserve` | **confirmed gap** — если заповедник в OSM размечен этим способом, на карте не появится вообще. Добавить параллельно в `polygons:100`, `lines:237`, `points:275` |
| `boundary=national_park` | не проверено отдельно | тоже отсутствует, стоит проверить есть ли нацпарки в целевом регионе с этим тегом |
| `information=guidepost` (+обязательный `tourism=information`) | подтверждено, de facto standard для путевых указателей на туристических/вело маршрутах | **confirmed gap**, отдельный от `amenity=signpost`. Сейчас `tourism=information` есть одним generic-типом — можно оставить как есть или выделить подтип |
| `historic=wayside_cross` | подтверждено, включая RU-версию Wiki: «встречается вдоль дорог в России» | **confirmed gap** — поклонные кресты, реальные навигационные ориентиры в лесу, тега нет вообще |
| `historic=wayside_shrine` | подтверждено | **confirmed gap** — придорожные часовенки/киоты, аналогично |
| `summit:cross=yes` | подтверждено как атрибут к `natural=peak`/`man_made=cross` | бонус, не критично |
| `natural=saddle` | **не подтверждено поиском**, была лишь гипотеза по памяти | требует отдельной проверки, не включать в работу как факт |

### Методика на будущее (согласовано с пользователем)
Идея пользователя: завести `inc/normalize_deprecated` — единая точка ре-маппинга
старых тегов в новые, подключаемая первым `include` во все геометрические файлы
(`points`/`lines`/`polygons`). Технически возможно — в стиле уже есть прецедент
переиспользуемых `include` (`inc/name` подключён трижды).

**Важные ограничения этого подхода** (проговорено, важно не забыть при реализации):
1. Не все замены 1:1 — например `boundary=protected_area` несёт доп. смысл
   (`protect_class`), которого нет у `leisure=nature_reserve`; для таких случаев
   правильнее не переписывать тег, а расширить условие в самом правиле отрисовки
   (как уже сделано для nature_reserve), а не нормализовывать.
2. Использовать `add`, не `set` — чтобы не затирать уже корректный новый тег, если
   оба тега почему-то сосуществуют на одном объекте: `oldtag=value & newtag!=* { add newtag=... }`
3. Подключать файл нормализации нужно во все geometry-файлы, где тег может
   встретиться (например shop-теги — это и `points`, и `polygons` для зданий-магазинов).

Пока реальных кандидатов на 1:1-нормализацию (кроме уже обработанной опечатки
cemetary/cemetery) не найдено — файл заводить рано, копить кандидатов по ходу
дальнейшего аудита.

## 4. Согласованные решения по консолидации POI (готово к внедрению)

### Еда → один тип
Заменяет `points:150-234` (27 правил, 20 типов `0x2a00-0x2a13`):
```
amenity=restaurant | amenity=cafe | amenity=fast_food | amenity=food_court [0x2a00 resolution 24]
```
Основание пользователя: данные на карте не всегда точны, детализация кухни не нужна;
название заведения всё равно видно в подписи; карта — для ориентирования, не точного
подбора, «для этого есть телефон».
**TYP на удаление:** `0x2a01-0x2a13` (19) + уже мёртвые `0x2a14-0x2a17` (4) = 23 типа.

### Продукты → один тип (включая мясную лавку)
Заменяет `points:329-363`:
```
shop=bakers | shop=bakery | shop=butcher | shop=convenience | shop=general | shop=organic | shop=supermarket {name '${name}'} [0x2e02 resolution 24]
```
**TYP на удаление:** `0x2e03`, `0x2e0a`, `0x2e0c`.

### Аптека — оставить отдельно (важно для безопасности)
```
shop=chemist [0x2e05 resolution 24]
```
Тип `0x2e05` (MPC: PHARMACY) — исправление найденной путаницы (см. раздел 1, п.6).

### Оптика — не выделять отдельно
Уходит в общий тип «прочие магазины» вместе со всем остальным непродуктовым.
*(Уточнение статуса: пользователь написал «можно смело убирать» — трактуется как
«не давать отдельный значок», НЕ «скрыть с карты полностью». Если имелось в виду
второе — требуется явное подтверждение.)*

### Велосипед — оставить отдельно (приоритет карты — вело-туризм)
```
shop=bicycle [0x2f13 resolution 24]
```
Мотозапчасти (`shop=motorcycle`) — НЕ сюда, уходят в авто-группу.

### Все остальные непродуктовые магазины → один общий тип
Заменяет `points:329-367` целиком (за вычетом продуктов/аптеки/велосипедов выше):
```
shop=* & shop!=no & shop!=none [0x2e00 resolution 24]
```
Покрывает: beauty, hairdresser, boat, car*, car_dealer, car_parts, car_rental,
car_repair, car_wrecker, tires/tyres, motorcycle, optician, clothes, fashion, shoes,
department_store, mall (объединены по решению пользователя), doityourself, furniture,
hardware, garden_centre и т.д.

**Порядок правил важен** — продукты/аптека/велосипеды должны идти РАНЬШЕ общего
catch-all правила (mkgmap берёт первое совпадение без `continue`).

**TYP на удаление (доп. к найденному по еде/продуктам):** `0x2f10`, `0x2f09`, `0x2f0d`,
`0x2f03`(сохранить под общий тип авто, либо тоже в 0x2e00 — уточнить), `0x2f07`,
`0x2f02`, `0x2f0a`, `0x2e08`, `0x2e07`, `0x2e01`+`0x2e04`, `0x2e09` — суммарно
**~37 TYP-слотов освобождается по всей группе еда+продукты+магазины**.

### Деревья/кусты — POI только для именованных
```
natural=tree & name=* ... (добавить условие name=* к существующим правилам inc/landuse_points:90-91)
natural=shrub & name=* ...
```
Безымянные — не должны порождать POI вообще.

### Опоры ЛЭП — убрать POI полностью
`points:297` `man_made=utility_pole [0x11506]` — удалить. Линии `power=line`/
`power=minor_line` не затрагиваются, остаются как есть.

## 5. TYP — найденные несоответствия MPC Name ↔ картинка (для справки, не срочно)

Все три примера ниже сейчас НЕ используются активными правилами (мёртвый код),
поэтому не горит, но это хорошие иллюстрации методологии на будущее:
- `0x1351d` — MPC: *RESTAURANT_PUNJABI*, авторские строки: «шиномонтаж»/«tyre service»
- `0x1351e` — MPC: *RESTAURANT_RAJASTHANI*, авторские строки: «Озон»/«» (маркетплейс)
- `0x13703` — MPC: *TAXI_STAND*, авторские строки: «горячий источник»/«hot spring»

**Договорённость с пользователем по методике чистки TYP:** сначала правильный
Type/SubType (для разумного fallback на встроенный Garmin-значок, если TYP не
подхватится на устройстве), потом объединение одинаковых картинок, потом дизайн.
Не наоборот. Ориентир для сверки типов — список из TYPViewer (программа, которой
пользователь редактирует TYP). Тест на реальном приборе — Garmin GPSMap 67
(нюанс: с прошивки ~8.80 у 67-й есть системная Etyp-прошивка, которая может
подмешиваться поверх стороннего TYP — при неожиданном виде символов сначала
исключить это, а потом уже грешить на свой TYP). Для быстрых итераций пользователь
использует QMapShack (свой рендерер, обычно точен, но не 100% идентичен
прошивке/BaseCamp — для критичных вещей сверять с реальным прибором).

**Полный граф `points/lines/polygons ↔ TYP` уже построен** (33 мёртвых TYP-записи,
17 активных правил без TYP-определения — см. историю чата, при необходимости
пересчитать скриптом `parse_typ.py`/`cross_reference3.py`).

## 6. Прочие находки (из отдельного независимого ревью, не полностью проверено вживую)
*(из более раннего REVIEW.md/REVIEW_URALLA_MASTER.md, часть уже покрыта выше)*
- `inc/access`/`inc/compat_lines`/`points`/`finalize` — логика access/barrier размазана по нескольким местам, дублируется. Согласован принцип «одна задача — одно место», конкретный план рефакторинга не составлен.
- `56 жёстко закодированных имён` (реки, вершины, `ref=М-5`) — предложение заменить на пороговые условия (`ele>=N`, `width>=N`) вместо списков имён. Не реализовано, требует решения пользователя по порогам.
- `make-cycleways` в `uralla.args` — подтверждено через официальную документацию mkgmap: **obsolete-опция, не имеет эффекта** в текущих версиях. Безопасно убрать.
- `cycle-map` в `uralla.args` — реальная опция, но офиц. документация прямо предупреждает «Don't use with the default style as that is a general style!». Стиль `uralla` унаследован от старого default-стиля mkgmap → требуется целенаправленное тестирование маршрутизации, не факт что это баг, но и не факт что безопасно.
- CRLF (Windows line endings) по всем файлам стиля — не проблема сама по себе, но будет шуметь в git diff при правках на других ОС. Решить сознательно (`.gitattributes`) один раз, не смешивать построчно.
- `relations`, `inc/access_country`, `inc/address` содержат правила для нерелевантных стран/сетей (US:I, US:US, AsianHighway, TAH, BEL/NLD/ESP и т.д.) — кандидаты на чистку, низкий приоритет.

## 7. Реструктуризация файлов (согласованный план, не реализовано)

Согласовано с пользователем: разбить `lines`/`points`/`polygons` на смысловые
секции (NORMALIZE → SPECIAL → TRANSPORT-группы → LABELS → FINALIZE для lines;
аналогично для points), **сохраняя порядок правил внутри секций** (функционально
важен из-за `continue`). НЕ сортировать алфавитно — только по смыслу.

**Комментарии — двуязычные (русский + английский), с тремя маркерами:**
- `[IMPORTANT/ВАЖНО]` — для критической логики (пример: building=yes→hut защита от add-pois-to-areas)
- `[INTENTIONAL/НАМЕРЕННО]` — для осознанных нестандартных решений (пример: taxi=yes на реках)
- `[CUSTOM/АВТОРСКОЕ]` — для авторских картографических решений

Реструктуризация — отдельный этап **после** логической чистки, не одновременно с ней.
