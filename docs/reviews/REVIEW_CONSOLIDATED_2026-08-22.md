# REVIEW_URALLA_CONSOLIDATED_2026-08-22.md

## Назначение

Единый рабочий master-review проекта Garmin OSM Topo / mkgmap style `uralla`,
консолидирующий:

1. решения пользователя, принятые в длительном аудите с ChatGPT;
2. свежий аудит Claude `TAGS_AUDIT_22_08.md`;
3. ранние `REVIEW.md` / `REVIEW_URALLA_MASTER.md`;
4. проверку реальных `styles/uralla/*`, `inc/*` и TYP там, где она уже выполнена.

**Статус:** аудит и проектирование. Реальные файлы стиля не менять до завершения
полного прохода и формирования одного согласованного патча.

### Приоритет источников при конфликте

1. Явное решение пользователя.
2. Подтверждённый факт из реального style/TYP.
3. Согласованный результат глубокого аудита конкретного блока (в т.ч. Claude).
4. Предложение/гипотеза модели.

Не принимать рекомендации любой модели автоматически. Если новый факт конфликтует
с ранее принятым решением — сначала проверить реальный код/TYP и только потом менять
master-list.

### Статусы

- **[KEEP]** — оставить.
- **[CHANGE]** — изменить.
- **[REMOVE]** — удалить из отображения/стиля.
- **[ADD]** — добавить поддержку.
- **[CHECK]** — требуется проверка.
- **[FUTURE]** — хорошая идея, но не текущая версия.

# 1. Концепция карты

Приоритеты:

1. лесной пеший туризм;
2. велотуризм;
3. пешая/велосипедная сеть городов и парков;
4. автомобильная навигация и остальные сценарии.

Главный критерий — качество готовой карты на небольшом Garmin-дисплее, а не
минимальный размер style или максимальная скорость сборки.

Принципы визуального дизайна:

- максимальный контраст;
- минимализм;
- минимум цветов;
- хорошо различимые линии и POI;
- не отображать техническую детализацию только потому, что она есть в OSM;
- редкий, но полезный ориентир не удалять только из-за низкой частоты.

Ночной вариант карты не нужен. Удаление `NightXpm`, `NightcustomColor` и прочей
night-логики — отдельный поздний этап, после логической чистки.

# 2. Важные исправления к ранним ревью

Эти пункты **заменяют** старые выводы, которые оказались слишком поверхностными.

## 2.1 `version` и `info:version` — НЕ конфликт

**[KEEP]**

- файл `version=1` — версия формата mkgmap style;
- `info: version=3.0` — авторская версия стиля.

Синхронизировать их не нужно.

## 2.2 `add name='туннель'` — не no-op

**[KEEP]**

`add` в mkgmap задаёт значение только если тег ещё не существует. Поэтому правило
для безымянных туннелей является рабочим fallback, а не ошибкой.

## 2.3 River routing через `taxi=yes` — намеренная авторская функция

**[KEEP]/[CHECK]**

Не удалять автоматически. Функция используется для направления/роутинга по рекам
и сплава через редко используемый профиль `taxi`.

Перед любым рефакторингом провести тесты на реальном Garmin/BaseCamp.

Маркер при реструктуризации:

`[INTENTIONAL/НАМЕРЕННО] river routing via taxi profile`

## 2.4 `opening_hours -> addr:postcode`

**[CHECK], не удалять автоматически.**

Вероятно исторический mkgmap-приём для вывода дополнительной информации на Garmin.
Он загрязняет адресный индекс, но сначала нужно определить, что пользователь реально
видит на приборе и зачем hack был введён.

## 2.5 Пустой `overlays` НЕ считать мусором

Ранее предлагалось удалить пустой файл. Свежий аудит выявил более важный смысл:
`overlays` — штатный механизм mkgmap для подсветки route relations.

**[KEEP]/[FUTURE]**

Пока он может оставаться пустым. В будущей версии возможна визуальная подсветка
hiking/mtb/bicycle relations через overlays.

## 2.6 `building=yes` в points

Реальная проблема не в массовом превращении зданий в избушки: `points` обрабатывает
узлы, а обычные здания-way идут через `polygons`.

Но семантика всё равно неверна.

**[CHANGE]**

- `tourism=wilderness_hut` / `tourism=alpine_hut` -> **0x2b07**, «избушка»;
- generic point `building=yes/true` -> отдельная семантика **«постройка»**, НЕ 0x2b07;
- при наличии явной туристической семантики она имеет приоритет над generic building.

Дополнительно задокументировать зависимость от `--add-pois-to-areas`, если эта
опция когда-либо будет включена.

# 3. Подтверждённые баги и обязательные исправления

## 3.1 АЗС

**[CHANGE]**

Текущее базовое `amenity=fuel [0x2f01 ...]` без `continue` перехватывает последующие
условия.

Финальная концепция:

- любая АЗС -> `0x2f01`;
- `amenity=fuel + shop=convenience` -> дополнительно `0x2e02` «продукты», подпись
  **«АЗС (продукты)»** там, где используется соответствующая подпись;
- HGV diesel `0x2f16` для туристической карты не нужен;
- дублирующие fuel-типы (включая водные) свести к одному после обратной проверки ссылок.

## 3.2 `surface=paved` ошибочно попал в «гравийку»

**[CHANGE]**

Убрать `surface=paved` из списков «гравийка» / «плохая гравийка».

## 3.3 Пустые имена

**[CHANGE]**

- `historic=memorial`: `${inscription}` -> fallback `памятник`;
- signpost: `${label}` -> fallback `указатель`.

Перед правкой учесть общую name-логику.

## 3.4 `shop=kiosk`

**[REMOVE]** как отдельную строку: её полностью покрывает общий `shop=*` catch-all.

## 3.5 Перепутанная семантика chemist/optician/garden_centre

**[CHANGE]**

- `shop=chemist` -> `0x2e05` (MPC PHARMACY);
- `shop=optician` -> общий непродуктовый магазин;
- `garden_centre` -> общий непродуктовый магазин.

# 9. Дороги: общая семантика покрытия

Карта должна прежде всего сообщать характер дороги, а не давать абстрактную оценку
«хорошая/плохая».

Фиксированные визуальные категории:

1. **гравийка**;
2. **плохая гравийка**;
3. **грунтовка**;
4. **плохая грунтовка**;
5. **ужасная грунтовка**.

Асфальт/нормальное твёрдое покрытие не требует отдельной положительной подписи.

В routing и визуальной классификации качество дороги не смешивать: ужасная грунтовка
может оставаться маршрутизируемой, но пользователь должен явно видеть её характер.

## 9.1 `surface=*`

Добавить/учесть современные значения в матрице, в частности:

- грунтовая группа: `ground`, `dirt`, `earth`, `woodchips` и другие подходящие;
- гравийная группа: `gravel`, `fine_gravel`, `compacted`, `pebblestone` с учётом
  `tracktype`/`smoothness`;
- `surface=snow` -> существующая логика winter road;
- `surface=ice` -> существующая логика ice road.

Не делать отдельные визуальные категории snow/ice.

## 9.2 `tracktype` и `surface`

`tracktype` — сигнал качества, но не готовая категория покрытия.

`surface` имеет приоритет для определения материала, `tracktype` и `smoothness`
корректируют состояние.

Архитектурная идея на финальный этап: вычислять внутренние признаки класса покрытия
и состояния, чтобы не дублировать огромную матрицу условий во всех highway-типах.
Решение о конкретных mkgmap-внутренних тегах принять после полного аудита.

## 9.3 `smoothness` overlay — принять результат глубокого аудита Claude

Это тот блок, который пользователь отдельно подробно разобрал с Claude и результат
его устраивает. Принимаем как authoritative design для текущего проекта:

```text
highway!=path & highway!=footway & highway!=cycleway & highway!=bridleway & highway!=steps & highway!=pedestrian
    & (smoothness=very_horrible | smoothness=impassable | smoothness=horrible)
    [0x1001a resolution 24 continue]

highway!=path & highway!=footway & highway!=cycleway & highway!=bridleway & highway!=steps & highway!=pedestrian
    & (smoothness=bad | smoothness=very_bad)
    [0x1001b resolution 24 continue]
```

- `0x1001b` = плохая дорога;
- `0x1001a` = ужасная дорога;
- overlay только для автомобильных/машинопроезжих типов;
- пешие/вело линии исключить.

## 9.4 `service=parking_aisle`

**[REMOVE] из визуального отображения полностью.**

Важно не просто удалить частное правило: parking aisle не должен затем попасть в
общий `highway=service` catch-all.

`forestry` / `agricultural` не делать отдельными важными визуальными классами.

## 9.5 LOD через `length()`

**[KEEP]** как сознательный механизм генерализации.

Не удалять/не упрощать только ради производительности.

Пороги пересматривать только после визуальных тестов и с учётом коротких связующих
участков туристических маршрутов.

# 10. Path / cycleway / footway и маршруты

## 10.1 Path -> cycleway

**[KEEP] намеренно:**

- `highway=path + bicycle=designated/official -> highway=cycleway`;
- `permissive` не равен designated и не обязан превращать path в cycleway.

Не считать это логическим дублем.

## 10.2 Маркированные hiking/bicycle/mtb relations — крупная новая находка

Свежий аудит Claude обнаружил важный пробел, который мы ранее не выделили:
маркированные туристические и веломаршруты практически не обрабатываются.

**[ADD]** минимальную relation-логику для переноса имени маршрута в way через
`mkgmap:trail_name`.

Концепция:

- `route=hiking`;
- `route=bicycle`;
- `route=mtb`.

Имена route relations использовать как fallback для безымянных way.

Дополнительное пользовательское решение:

**way, входящие в маркированный маршрут, показывать на одну ступень zoom дальше**, без
новой графики TYP.

Порог-кандидат `length()>100`; расписать отдельно для:

- footway;
- cycleway;
- path (обе ветки);
- track (обе ветки);
- bridleway (LOD-окно добавить с нуля).

**[FUTURE]** overlays для цветовой/сетевой подсветки `lwn/rwn/nwn` после теста на
реальных маршрутах.

## 12.2 Narrow gauge

## 12.3 Метро

Пользовательское решение:

## 12.4 Заброшенные/неиспользуемые пути

Она соответствует пользовательской картографической практике: пересыхающий исток ->
ручей -> река.

## 13.4 Канавы

Пользователь выбрал вариант А:

- `waterway=ditch` показывать **только на самом ближнем уровне** (`resolution 24`);
- удалить/не использовать правило, вытягивающее ditch на `resolution 21-23`.

## 13.5 Drain и canal

Пользовательская концепция: визуально трактовать их **как ручьи**, а не плодить
отдельные стили.

При этом:

- сохранить техническую river-routing семантику, если она нужна;
- для `drain + intermittent=yes` сохранить различие пересыхания;
- точную LOD-реализацию drain/canal определить в детальном `waterway=*` проходе.

## 13.6 Водопады

Точка **[KEEP]**. Дополнительная waterfall-line не нужна, если она не несёт отдельной
полезной информации.

## 13.7 Водные полигоны

**[KEEP]** существующую `area_size()`-генерализацию `natural=water`:
крупные водоёмы видны дальше, мелкие — ближе.

Не переписывать эту систему поверхностно.

## 13.8 Wetlands

Существующая детализация `swamp/marsh/wet_meadow/tidalflat/reedbed/saltmarsh`
полезна и требует отдельного детального полигона-аудита, а не упрощения вслепую.

# 14. Boundary / охраняемые территории

Свежий аудит Claude закрывает ранее найденный gap.

**[ADD/KEEP]** в line/polygon-логике:

- `boundary=protected_area` (+ `protect_class=*`);
- `boundary=national_park`.

Использовать существующую визуальную логику nature reserve / границы.

Пользовательское решение: **не добавлять отдельный POI-центр заповедника/нацпарка**.
Граница важнее единичной точки.

`boundary=national` и `boundary=political` -> **[CHECK]/likely REMOVE** после проверки
реального использования; не трогать автоматически.

# 16. TYP — методика и конкретные решения

## 16.1 Главный принцип

Сначала:

1. правильный Garmin Type/SubType / MPC Name;
2. корректный fallback при сбое/неподхвате TYP;
3. объединение дублирующих картинок;
4. только потом визуальная перерисовка.

Это повышает устойчивость карты при проблемах со сборкой/TYP на реальном приборе.

## 16.2 Проверка на приборах

- быстрые проверки: QMapShack;
- критичные визуальные/fallback проверки: реальный Garmin GPSMap 67 / BaseCamp;
- учитывать возможное влияние системной Etyp-прошивки GPSMap 67.

## 16.3 Известные несоответствия

Неиспользуемые/мёртвые примеры:

- `0x1351d` MPC RESTAURANT_PUNJABI, картинка шиномонтажа;
- `0x1351e` MPC RESTAURANT_RAJASTHANI, Ozon;
- `0x13703` MPC TAXI_STAND, hot spring.

Они подтверждают необходимость полного MPC-аудита.

## 16.4 Новые картинки TYP

Нужны в TYPViewer:

- `0x6602` -> «завал»;
- `0x11602` -> «пещера».

## 16.5 Авторские POI, которые не удалять

- ЖД сигналы;
- ЖД пикеты;
- две категории антенн/вышек связи — существующие два TYP оставить;
- редкие интересные авторские символы.

## 16.6 Night mode

**[FUTURE REMOVE]** после завершения основной логики.

# 17. `inc/*` и архитектура

Нельзя анализировать только `lines/points/polygons`: часть ключевой семантики уже
находится в `inc`.

Особенно важны:

- `inc/water_lines`;
- `inc/water_points`;
- `inc/water_polygons`;
- `inc/landuse_points`;
- `inc/landuse_polygons`;
- `inc/access`;
- `inc/roadspeed`;
- `inc/name`;
- compat-файлы.

При финальной реструктуризации:

- смысловые секции, а не алфавитная сортировка;
- сохранить порядок правил и `continue`-семантику;
- двуязычные комментарии RU/EN;
- маркеры:
  - `[IMPORTANT/ВАЖНО]`;
  - `[INTENTIONAL/НАМЕРЕННО]`;
  - `[CUSTOM/АВТОРСКОЕ]`.

## 17.1 `normalize_deprecated`

Идея хорошая, но файл не создавать «для галочки».

Создать только когда накопится достаточное число безопасных 1:1 legacy -> current
ремаппингов.

Для семантически более богатых новых схем (`boundary=protected_area`) расширять
основное условие, а не уничтожать смысл грубой нормализацией.

# 22. Политика изменений

До завершения аудита не вносить разрозненные изменения в production-style.

Финальная реализация должна быть одним согласованным комплектом:

- `points`;
- `lines`;
- `polygons`;
- `relations`;
- `inc/*`;
- `TYP`;
- args/options только если подтверждена необходимость.

Для каждого изменения подготовить changelog: **что изменено / почему / какой риск /
как проверить**.
