# Backlog

Накопленные идеи, открытые задачи и важные уже принятые решения проекта.

Идентификаторы задач постоянные: после назначения ID не переиспользуется, даже если задача закрыта или отменена. Это позволяет ссылаться на задачу коротким кодом без цитирования длинного описания.

Статусы:

- `OPEN` — задача открыта;
- `PARTIAL` — часть решения уже реализована;
- `DONE` — задача закрыта, решение сохраняется здесь как проектное знание;
- `HOLD` — намеренно отложено.

## Packaging / BaseCamp / MapSource

### PACK-01 — One-click installer for BaseCamp / MapSource — OPEN

Для Mapsource-архива добавить Windows-скрипты установки и удаления карты.

Цель: пользователь не должен вручную искать системный каталог Garmin или разбираться в плохо очевидном механизме добавления карт в BaseCamp / MapSource.

Предлагаемое поведение установщика:

- найти корректный пользовательский каталог Garmin;
- скопировать туда комплект карты в отдельную папку продукта;
- при необходимости выполнить регистрацию карты для BaseCamp / MapSource;
- повторный запуск должен обновлять уже установленную карту, а не создавать дубликат;
- после успешной установки открыть папку назначения в Explorer;
- рядом положить отдельный uninstall-скрипт для корректного удаления карты.

Ожидаемые имена файлов в архиве:

- `install-map.cmd` (или CMD-обёртка над PowerShell);
- `uninstall-map.cmd`.

## Names / map labels

### NAME-01 — Ограничение чрезмерно длинных `name` — PARTIAL

Для компактного экрана Garmin принят предел: исходный OSM `name` длиной до 30 символов включительно считается допустимым; при длине 31+ постоянная подпись карты должна заменяться коротким обозначением типа объекта, а исходный OSM `name` не должен уничтожаться.

Текущий механизм препроцессора уже помечает такие объекты служебным тегом `uralla:long_name=yes` при `len(name) > 30`.

Проверка на `historic=monument` успешно пройдена: длинная поэма вместо постоянной подписи отображается как `памятник`.

Открытая часть: распространить правило на остальные `name` и затем закрыть задачу.

### NAME-02 — Семантическая очистка географических подписей — DONE

Для географических объектов препроцессор сохраняет исходный OSM `name=*`, но при очевидном дублировании типа объекта создаёт отдельную отображаемую подпись `uralla:label=*` без ведущего родового слова.

Правило применяется только к согласованным классам и только к началу строки:

- `natural=peak|volcano`: `Гора Иремель`, `г. Иремель` → `Иремель`;
- `natural=ridge`: `Хребет Нурали`, `хр. Нурали` → `Нурали`;
- озёра (`water=lake` или legacy `natural=lake`): `Оз. Белое` → `Белое`;
- `natural=waterfall`: `Водопад Кивач`, `вдп. Кивач` → `Кивач`.

Родовое слово в конце или внутри собственного имени не удаляется: `Большая Гора`, `Белая Гора`, `Черное Озеро`, `Каменный Хребет` остаются без изменений. Глобальная очистка по регулярному выражению запрещена: типовой термин удаляется только когда он согласуется с OSM-тегами объекта.

## POI / Garmin types

### POI-01 — Аудит POI и перенос группы `0x115` в безопасный диапазон — DONE

Целевой объём этого этапа был ограничен пользовательскими POI группы `0x115`. Группа полностью освобождена: в production style и TYP больше нет активных `0x115xx` точек.

Итоговые подтверждённые переносы и их текущие адреса зафиксированы в `docs/POI_115_MIGRATION.md`; `tests/test_group_115_migration.py` не допускает возврата старой группы.

При переносах одновременно перемещались соответствующие TYP-блоки с исходной графикой, поэтому новые style-адреса не теряют пользовательские символы.

## Polygon rules

### POLY-01 — Аудит правил полигонов — OPEN

Текущий основной приоритет по стилю.

Последовательно пройти `styles/uralla/polygons` и подключаемые polygon include-файлы: проверить смысловое соответствие OSM-тегов Garmin polygon types, широкие fallback-правила, системные подписи Garmin, ложные заливки, порядок перехвата правил и случаи, где площадное отображение вообще не требуется.

Аудит уже начат по результатам реальной проверки карты:

- площадные `highway=footway|pedestrian|...` вынесены с системного `0x0d` (Garmin Reservation) на custom polygon, чтобы прибор не показывал «Резервация, заповедник»;
- `place=*` polygon rules больше не перехватывают объекты с `building=*`, чтобы здания не отображались как `населёнка`.

Работать небольшими смысловыми группами и после каждого изменения сверять style + TYP + поведение на Garmin.

## Build pipeline / performance

### BUILD-01 — Параллельный preprocess после splitter — OPEN

Исследовать перестройку pipeline так, чтобы OSM-данные нарезались splitter до объединения с DEM, после чего отдельные OSM-тайлы обрабатывались препроцессором параллельно по ядрам.

Предлагаемая схема:

- splitter один раз вычисляет `areas.list` по OSM;
- OSM режется по этим областям;
- elevation/изолинии режутся отдельно тем же `areas.list`;
- каждый OSM-тайл проходит preprocess независимо и параллельно;
- обработанный OSM-тайл объединяется с соответствующим elevation-тайлом по mapid;
- готовые пары передаются в mkgmap.

Цель: убрать однопоточный preprocess большого регионального PBF из критического пути и не заставлять Python повторно просматривать объекты изолиний, которые препроцессору не нужны.

## Aeroway / airfields

### AERO-01 — Активные runway/taxiway не участвуют в автомобильном routing — DONE

Активные авиационные пути остаются визуальными объектами без `road_class`/`road_speed`:

- `aeroway=runway` использует Garmin line type `0x27`;
- `aeroway=taxiway|taxilane` использует `0x1a`.

### AERO-02 — Заброшенные твёрдые аэродромные пути использовать как дороги — DONE

Заброшенные/неиспользуемые paved runway сохраняют авиационный вид `0x27`, но получают отдельный невидимый routing-carrier `0x1b` с автомобильной маршрутизацией.

Заброшенные/неиспользуемые paved taxiway/taxilane используют `0x1a road_class=1 road_speed=4` и становятся проезжаемыми.

### AERO-03 — Taxiway должна прорисовываться под runway — DONE

Изначальная проблема была визуальной: рулёжная дорожка прорисовывалась поверх ВПП. Геометрический постпроцессор для этой задачи не нужен.

Решение оказалось проще: runway оставлена на `0x27`, а taxiway/taxilane переведена на отдельный Garmin type `0x1a`. После разделения типов порядок прорисовки стал правильным: taxiway находится под runway.

Это решение уже закреплено текущим style и тестами и не должно снова превращаться в задачу по геометрическому postprocess.
