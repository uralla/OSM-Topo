# REVIEW_URALLA_MASTER.md

## Назначение

Рабочий master-review для совместного аудита стиля mkgmap `uralla`.

**На этом этапе исходные файлы не изменять.** Сначала закончить аудит, затем сформировать единый согласованный комплект файлов.

---

## 1. Концепция карты

Приоритеты:

1. пеший туризм и походы;
2. велотуризм;
3. пешеходная и велосипедная сеть в городах, особенно парках;
4. остальные сценарии, включая автомобильную навигацию.

Главный критерий — **качество готовой карты**, а не скорость сборки.

Сборка выполняется на старом резервном Ubuntu-компьютере с намеренно сниженной частотой CPU. Полная сборка спокойно может выполняться около суток. Поэтому не жертвовать качеством ради ускорения на минуты/часы.

---

## 2. Генерализация

`length()` используется намеренно как механизм LOD.

На максимальных масштабах линии должны быть полноценными. На дальних — короткие/второстепенные линии удаляются для борьбы с визуальным мусором.

Поэтому:

- не удалять `length()` только ради производительности;
- особенно осторожно относиться к коротким соединительным участкам туристических и велосипедных сетей;
- сначала оценивать картографический результат.

---

## 3. Велосипедная логика

`highway=path` без дополнительных тегов должен оставаться пригодным для соответствующей маршрутизации.

Если:

```text
bicycle=designated
bicycle=official
```

то намеренно выполняется:

```text
highway=path -> highway=cycleway
```

Цель — визуально показать явно предназначенную для велосипеда дорожку как велодорожку.

Это **не считать дублированием**.

При аудите проверять:

```text
OSM tags
  -> path/cycleway/footway
  -> inc/access
  -> mkgmap:bicycle / mkgmap:foot
  -> road_class / road_speed
  -> Garmin routing
```

Особое внимание — городским паркам.

## 7. АЗС

В текущем `points` есть:

```text
amenity=fuel [0x2f01 resolution 24]
amenity=fuel & fuel:HGV_diesel=yes [0x2f16 ...]
amenity=fuel & shop=convenience [0x2e06 ...]
```

Первое правило без `continue`, поэтому последующие два недостижимы.

Это подтверждённый логический баг.

Предпочтительный результат:

```text
amenity=fuel
    -> 0x2f01  (один символ АЗС)

amenity=fuel + shop=convenience
    -> дополнительно 0x2e02 (продукты)
```

HGV diesel `0x2f16` для туристической карты не нужен и может быть удалён.

Также обнаружено:

```text
waterway=fuel -> 0x2f01
waterway=fuel -> 0x11603
```

на одном resolution. `0x2f01` и `0x11603` имеют одинаковую графику АЗС. Оставить один тип после проверки всех ссылок.

## 24. splitter -> mkgmap -> packaging -> tile identity/ranges

### 24.1 Что подтверждено по реальным сборочным скриптам

Проверены `scripts/all.sh` и 27 региональных скриптов. В каждом региональном
скрипте есть по одному вызову splitter и mkgmap.

Для всех 27 карт подтверждено:

- `--mapid` splitter задан явно;
- `--family-id` mkgmap задан явно;
- стартовые map ID уникальны;
- family ID уникальны;
- `--product-id` не задан, поэтому используется документированный default
  `PID=1`;
- подключается готовый бинарный `../../styles/uralla.typ`;
- `--overview-mapname` задан;

### 24.2 Диапазоны тайлов

Splitter назначает последовательные ID, начиная с `--mapid`. Поэтому
статическая проверка стартовых чисел недостаточна: нужен фактический размер
каждого `areas.list`.

Расстояние между соседними зарезервированными стартами составляет:

- 1000 ID для legacy-схемы;
- 10000 ID для current-схемы.

Без учёта отдельного overview-ID соседние tile ranges не пересекутся, если
карта использует не более соответственно 1000 или 10000 тайлов. Для полного
блока, где нулевой номер резервируется под overview, безопасная ёмкость
составит 999 или 9999 тайлов:

| Схема | Overview | Tile range | Макс. тайлов |
|---|---:|---:|---:|
| legacy | `FID*1000` | `FID*1000+1 .. FID*1000+999` | 999 |
| current | `FID*10000` | `FID*10000+1 .. FID*10000+9999` | 9999 |

Окончательно закрыть диапазоны можно только по сгенерированным
`areas.list`/ `template.args` актуальной сборки либо по машинному отчёту
валидатора, который читает эти файлы.

### 24.3 Подтверждённый packaging-риск: общий overview ID

Во всех 27 сборках отсутствует `--overview-mapnumber`. При включённом
`--tdbfile` mkgmap использует default `63240000`, поэтому разные GMAPI/TDB
продукты получают одинаковый внутренний overview map number.

Это не доказывает повреждение каждого отдельного пакета, но создаёт ненужный
риск коллизий при одновременной установке нескольких продуктов. В change set
следует назначить overview-ID из того же зарезервированного блока, например
`first_mapid - 1`:

- `ural-n`: `01018000`;
- `kz`: `10500000`;
- `armenia`: `10530000`.

После выбора схемы validator должен запрещать общий default и проверять
уникальность overview-ID вместе с tile ID.

Документация:

- <https://www.mkgmap.org.uk/doc/options>
- <https://www.mkgmap.org.uk/doc/splitter.html>

### 24.4 Бинарный TYP и FID/PID

Исходный `uralla.typ` декомпилируется как `FID=1002 / PID=1`, тогда как
региональные карты используют разные FID. Для текущего способа вызова это не
является mismatch готового пакета.

В mkgmap класс `TypSaver` читает FID/PID готового бинарного TYP и, если они
не совпадают с `--family-id` / `--product-id`, переписывает поля TYP перед
упаковкой. Поэтому один исходный бинарный `uralla.typ` может использоваться
для всех региональных продуктов; в итоговом артефакте нужно лишь
контролировать, что mkgmap действительно завершился успешно.

Исходный код механизма:

- <https://github.com/openstreetmap/mkgmap/blob/master/src/uk/me/parabola/mkgmap/main/TypSaver.java>

### 24.5 Стабильность tile identity

Поскольку ни один скрипт не передаёт splitter `--split-file`, каждое
обновление заново рассчитывает границы областей. Последовательность map ID
сохраняется, но конкретная географическая область, соответствующая номеру,
может измениться.

Для воспроизводимой сборки следует:

1. сохранять отдельный `areas.list` для каждого продукта;
2. повторно использовать его через `--split-file`;
3. регенерировать осознанно, отдельной версией диапазона, когда рост данных
   больше не помещается в прежнее разбиение;
4. после splitter проверять первый/последний ID и количество тайлов.

### 24.6 Старые региональные scripts: только источник миграции

В `scripts/all.sh` вызов Грузии записан как абсолютный путь
`/georgia.sh` вместо `./georgia.sh`. Это объясняет, почему старая ручная
оркестрация может пропускать карту, но **исправлять и далее сопровождать
`all.sh` и 27 дублирующих региональных scripts не требуется**.

Принятое архитектурное решение — заменить их единой автоматизированной
сборочной системой. Legacy scripts используются только для:

- извлечения существующих параметров каждой карты;
- заполнения registry/manifest;
- проверки, что новая система сохраняет границы продуктов, названия,
  источники, polygon/DEM-настройки и существующие map identities;
- сравнения результатов на этапе миграции.

Ошибка `/georgia.sh` становится приёмочным тестом: карта `georgia` должна
быть активна в manifest и гарантированно попадать в очередь общего runner.
Отдельная правка legacy `all.sh` в change set не нужна.

### 24.7 Новая автоматизированная сборочная система

Единственный источник параметров сборки — registry/manifest. Принятая
архитектура зафиксирована в [`docs/BUILD_SYSTEM.md`](docs/BUILD_SYSTEM.md), а
первичная миграция всех 27 продуктов — в
[`config/maps.yaml`](config/maps.yaml). Для каждой карты manifest хранит как
минимум:

```text
product_key
enabled
priority
source
polygon
elevation_source
family_id
product_id
overview_mapnumber
first_tile_mapid
reserved_tile_count
family_name
series_name
output_name
areas_list_path
update_interval
per_map_overrides
```

Один общий runner выполняет одинаковую контролируемую цепочку:

```text
download/update source
  -> extract product polygon
  -> place/address transform
  -> semantic preprocessor
  -> merge external elevation/contour PBF
  -> splitter
  -> mkgmap
  -> packaging/range validator
  -> publish Garmin packages
```

Планировщик выбирает следующую карту сначала по приоритету, затем по степени
просроченности обновления. Для каждого запуска хранится история и метрики по
стадиям:

- результат и причина ошибки;
- время выполнения;
- пиковая RAM;
- использование swap;
- дисковый I/O;
- количество и диапазон тайлов;
- версии входных данных, splitter, mkgmap, style и TYP.

Validator автоматически проверяет:

- восьмизначное представление и уникальность map ID;
- число тайлов в зарезервированном блоке;
- отсутствие пересечений tile/overview ranges;
- уникальность `FID/PID` продукта;
- соответствие FID/PID TYP после упаковки;
- отсутствие двух входных IMG с одинаковым внутренним map ID;
- наличие ожидаемого артефакта для каждой активной карты.

Таким образом, все будущие исправления сборочной логики выполняются один раз в
общем runner/validator или manifest, а не размножаются по региональным shell-
скриптам. Semantic preprocessor стоит до слияния внешних контуров высот, чтобы
обрабатывать только исходные OSM-объекты и их relations.

## 25. Механическая сверка lines <-> TYP## 25. Механическая сверка lines <-> TYP

Проверка выполнена по `lines`, `inc/contour_lines`, `inc/water_lines` и
декомпилированному основному `uralla.typ`.

| Показатель | Количество |
|---|---:|
| активные line types в style | 77 |
| line types в TYP | 92 |
| активные line types без TYP | 0 |
| TYP line types без активного правила | 15 |

Все линии, реально создаваемые style, имеют определение в TYP.

Не используются активными правилами:

```text
0x10106 0x10107 0x10108 0x10d1f 0x10f06
0x10f1c 0x12d07 0x14 0x1b 0x26
0x2c 0x2f 0x08 0x09 0x0c
```

Часть из них встречается только в закомментированных правилах:

- `0x1b` — старые ferry rules;
- `0x0c` — старый блок roundabout;
- `0x08` — старое правило link;
- `0x14` — старое общее railway rule;
- `0x12d07` — отключённое правило природной поверхности.

Остальные являются кандидатами на удаление из итогового TYP после
контрольной проверки исходника TYP, но не должны удаляться из текущего
комплекта до формирования единого change set.

Совпадающая графика найдена только у двух пар/групп:

- `0x09` и `0x0c` — оба line type сейчас не используются;
- `0x10f01` и `0x10f03` — соответственно gondola и chair_lift, оба активны.

Вторую пару пока оставить: одинаковый рисунок не является достаточным
основанием смешивать разные виды подъёмников.

## 26. Механическая сверка points <-> TYP

Проверка выполнена по `points`, `inc/landuse_points`, `inc/water_points` и
декомпилированному основному `uralla.typ`.

| Показатель | Количество |
|---|---:|
| активные point types в style | 170 |
| point types в TYP | 169 |
| активные point types без определения в TYP | 17 |
| TYP point types без активного правила | 16 |

### 26.1 Активные types без собственного TYP-оформления

```text
0x2100 0x210f 0x2c01 0x2c07 0x2c0a
0x2d04 0x2d05 0x2f02 0x2f09 0x2f0c
0x2f13 0x3006 0x5a00 0x650a 0x650c
0x650f 0x6612
```

Это не означает автоматическое исчезновение POI: для обычных Garmin types
может использоваться встроенное оформление устройства. Но внешний вид тогда
не контролируется нашим TYP и может различаться между устройствами и BaseCamp.

Особенно проверить на реальном Garmin туристически значимые:

```text
0x5a00  signpost
0x650a  glacier
0x650f  basin/reservoir point
0x6612  nature reserve
```

Для них предпочтительно либо сознательно подтвердить встроенную графику, либо
добавить минималистичные символы в итоговый TYP.

### 26.2 TYP types без активного правила

```text
0x11602 0x1351d 0x1351e 0x13703
0x2a14 0x2a15 0x2a16 0x2a17
0x2e0b 0x2e0d 0x2f18
0x4500 0x4600 0x6402 0x6602 0x0a00
```

Предварительная классификация:

- `0x11602` — графический дубль активного `0x2c0b`, правило закомментировано;
- `0x2a14..0x2a17` — неиспользуемые кухонные разновидности;
- `0x2f18` — отключённый internet POI;
- `0x4500`, `0x4600` — старые restaurant/bar types;
- `0x6402` — старый общий building POI;
- `0x13703` — старый hot spring, тогда как активное правило использует
  `0x6511`;
- `0x6602` — старые stones, тогда как `natural=rock` использует `0x6607`;
- `0x0a00` — старый locality, активное правило использует `0x11504`;
- `0x1351d`, `0x1351e`, `0x2e0b`, `0x2e0d` рассмотреть вместе с согласованным
  упрощением магазинов и сервисов: часть удалить, а `0x2e0d` при желании
  можно переиспользовать как единый общий магазин.

### 26.3 Подтверждённые визуальные дубли points

- `0x2a00..0x2a13` — 20 ресторанных/кухонных types имеют один и тот же XPM;
- `0x2e00`, `0x2e01`, `0x2e03`, `0x2e04`, `0x2e06..0x2e0d` — 12 магазинных
  types имеют один и тот же XPM;
- `0x2a14..0x2a17` — ещё четыре одинаковых, но уже неиспользуемых кухонных
  types;
- `0x2f01` и `0x11603` — одинаковая графика АЗС;
- `0x11602` и `0x2c0b` — одинаковая графика place of worship;
- `0x0900` и `0x0b00` — одинаковая графика village/hamlet.

Это механически подтверждает ранее согласованное решение:

- кухни можно объединить без визуальной потери;
- магазины можно объединить без визуальной потери;
- дублирующий `waterway=fuel -> 0x11603` можно убрать;
- village/hamlet пока оставить разными Garmin types из-за различий классов и
  resolution, несмотря на одинаковый рисунок.

Статическая сверка считает правило синтаксически активным, даже если оно
недостижимо из-за более раннего правила без `continue`. Поэтому ранее найденный
баг `amenity=fuel` остаётся в силе: `0x2f16` и `0x2e06` в этой ветке фактически
не достигаются.

## 27. Место препроцессора в цепочке

Согласованная последовательность:

```text
исходный OSM PBF
  -> semantic preprocessor
  -> enriched OSM PBF
  -> splitter
  -> mkgmap
  -> packaging/range validator
  -> Garmin packages
```

Препроцессор должен выполняться **до splitter**, чтобы связь целой реки с её
`type=waterway` relation была разобрана один раз, а служебный ранг был перенесён
на все нужные member ways до нарезки тайлов.

### Реки

Не вычислять длину геометрически. Использовать заранее собранный каталог
опубликованных данных и сопоставление преимущественно по `wikidata=Q...`.

На линии передавать:

```text
uralla:river_rank=1..4
uralla:manual_keep=yes
```

Текущие 29 авторских рек сохраняются в каталоге как обязательное ядро.

### Вершины

Не вычислять высоту, prominence и isolation. Использовать опубликованные
значения и сопоставление с `natural=peak` / `natural=volcano` по
`wikidata=Q...`, с контролируемым fallback по имени и координатам.

На узлы передавать:

```text
uralla:peak_rank=1..4
uralla:manual_keep=yes
```

Текущий авторский список вершин сохраняется как обязательное ядро.

Каталог проектировать сразу для Европы и Азии. Style переводить с имён на
`uralla:*_rank` только после проверки каталога на текущих картах. До этого
жёсткие списки не удалять.
